# Backend durability method

## Scope delivered

The API now has an explicit PostgreSQL runtime selected by `DATABASE_URL`. It persists consumer and administrator identities and hashed sessions, reasoned administrator role grants and access audit, append-only identifiable-support access receipts, versioned feature flags and change audit, revisioned profiles, bounded analytics dimensions, recipe author/review/publication history, verified entitlement snapshots and App Store event metadata, plan lifecycle/history, ratings/reviews, grocery/prep/meal operational state, account export/deletion requests, and durable background jobs. Memory mode remains the safe local default.

Reviewer-gated ingestion transactionally stores verified ingredients, household conversions, immutable nutrient sources/records, reviewer identity, and content audit evidence. A reviewer-only inventory reconstructs conversions, per-100 g values, source identity, licence, confidence, and effective dates for the Control Room after refresh. Catalogue drafts retain their complete authoring payload, while submission and approval validate that database-backed evidence before normalizing child rows. Published versions snapshot recipe timing, slots, ingredient names/categories/allergens, and nutrient provenance; the planner reads only the active published pointer. App Store ingress persists stable per-account purchase tokens and a verified notification inbox. Scheduled entitlement reconciliation discovers due Apple-linked subscriptions, creates idempotent leased jobs, verifies Apple-signed status history, and applies only identity-matched results.

## Transaction boundaries

- A checked-out PostgreSQL client owns each transaction from `BEGIN` through `COMMIT` or `ROLLBACK`; it is always released.
- Profile writes use compare-and-set revisions so stale devices cannot silently overwrite newer answers.
- Recipe succession is serialized per recipe. Draft creation, submission, rejection, independent-review publication, active-version pointer changes, and audit evidence each commit atomically; one partial unique index prevents competing open versions.
- Published recipe-version rows and all normalized ingredient, step, and nutrient-evidence children are database-guarded against mutation. Recipe timing and eligible slots are copied into version metadata so a later draft cannot alter an active published snapshot.
- Ingredient writes replace their conversion set and audit the reviewed payload in one transaction. Published recipe children retain ingredient display/category/allergen snapshots, while nutrient rows and sources become database-immutable once cited by a published recipe.
- A verified App Store event, entitlement snapshot, and event-processing marker commit together.
- A reasoned operator subscription retry locks the case, schedules a verified reconciliation job, and appends immutable operator/correlation evidence together; it does not change entitlement access.
- Each export/deletion request and its idempotent background job commit together.
- Each plan request and its leased job commit together; a complete immutable week, plan items, groceries, prep and terminal job state materialize in one worker transaction.
- Each confirmed meal swap commits an immutable successor plan/items, recipe-version audit, recalculated groceries/prep, compatible operational state, and adoption handoff together.
- Account erasure deletes user-owned relational data and completes its audit receipt in one transaction.
- Materialized plans remain immutable. Only the erasure worker can opt into the transaction-local `nourish.account_deletion` setting required to remove them.

## Authentication trust boundary

Raw access, refresh, and magic-link tokens are never stored. Database lookups use SHA-256 token hashes; magic links are single-use; refresh rotates into a replacement session; revocation can target one or all sessions. Device assertions cannot change access. The ingress verifies StoreKit transaction JWS values and App Store Server Notifications V2 outer/transaction/renewal JWS values; the reconciliation adapter authenticates Apple's status-history request and verifies its results. Both use the configured bundle, environment, application ID, product allowlist, and Apple trust roots. Production credentials and live signed fixtures are not present in this workspace.

Administrator identity assertions cross a separate verifier boundary and must contain MFA before an eight-hour access session can be issued. Only a SHA-256 token hash is persisted. Active, reasoned role grants are resolved on every protected request; `security_admin` is the explicit override. Session exchange, grant/deny decisions, revocation, and provisioning are recorded in append-only access audit with route and correlation identity. The shared admin key is retained only as an explicit local-development fallback. A production workforce identity provider and its company sign-in callback are not configured in this workspace.

## Durable job semantics

Jobs are idempotent by job type and idempotency key. A worker atomically claims one eligible row with a lease, increments its bounded attempt count, and records its worker identity. Expired leases are reclaimable. Failures return to the queue with capped exponential delay until the maximum attempt count, after which they become dead jobs. Type filters ensure a worker claims only registered work. The reconciliation scheduler locks due rows with `SKIP LOCKED`, excludes queued/running duplicates, and keys each job by account plus saved due time; a successfully repeated Apple event refreshes the next due time without replaying stale access.

## Privacy execution

The export worker writes a versioned JSON document through a private object-store interface. Production configuration composes an S3-compatible adapter with mandatory authenticated application-level encryption, no-store metadata, safe logical keys, optional tenant/environment prefix, standard workload credentials, exact deletion, and paginated account-prefix deletion. Optional provider-side encryption remains available as defense in depth. It includes account identity metadata, the profile, subscription snapshot, plans and plan items, adoptions and swaps, groceries, prep, operational state, sync journal, meal feedback, and weekly reviews. It deliberately excludes magic-link and session token hashes and App Store signed payloads.

The deletion worker removes prior export objects, then erases user-owned relational history, authentication state, profiles, subscriptions, plans, feedback, groceries, prep, and mutation journals. The deletion request retains only its pseudonymous subject hash and completion timestamp for operational evidence. Independently, the scheduled retention scanner physically deletes expired customer and administrator export objects by exact validated key, clears the key conditionally, and writes append-only success or controlled-failure evidence.
