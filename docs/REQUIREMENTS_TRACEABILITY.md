## Architecture decisions

| Layer | Recommendation |
|---|---|
| iOS client | Swift + SwiftUI; async/await; StoreKit; APNs; Keychain; local persistence/cache |
| Admin web | Next.js + TypeScript; server-rendered authenticated routes; accessible charting and tables |
| Backend API | TypeScript service using NestJS/Fastify or equivalent; REST; OpenAPI contract |
| Primary database | Managed PostgreSQL with migrations, row-level ownership controls, point-in-time recovery |
| Background jobs | Managed queue for plan generation, notifications, exports, subscription reconciliation |
| Cache/coordination | Redis-compatible managed cache for idempotency, rate limiting, and short-lived jobs |
| Object storage | Private encrypted storage for exports and content assets with expiring signed access |
| Analytics | First-party product events forwarded to a privacy-appropriate analytics/warehouse layer |
| Monitoring | Crash reporting, server error tracing, structured logs, uptime checks, and alerting |

## Release-blocking acceptance criteria

- [ ] Zero known P0 or P1 security, privacy, entitlement, allergen, or nutrition-calculation defects.
- [ ] Every hard-exclusion test fixture produces zero violating plan items and swap candidates.
- [ ] All P0 user journeys pass on supported devices in production-like staging.
- [ ] StoreKit purchase, trial where enabled, renewal, cancellation, expiration, refund/revocation, and restore are tested in sandbox/test environment.
- [ ] Account export and deletion complete end-to-end with auditable state transitions.
- [ ] Dashboard KPIs reconcile against controlled test data and show metric definitions/freshness.
- [ ] Crash-free and plan-latency thresholds are met during beta at agreed sample size.
- [ ] Privacy policy, terms, wellness disclaimer, support information, and App Store privacy details are approved and consistent.
- [ ] Production monitoring, alerts, on-call contacts, rollback, backup, and incident procedures are active.

## Status discipline

- `verified`: implemented and covered by an executable check or build verification.
- `partial`: some required behavior exists, but the complete requirement is not met.
- `design_only`: represented in prototype/design, without production behavior.
- `contract_only`: typed route, schema, or error contract exists, without production service behavior.
- `not_started`: no implementation evidence recorded.
- `blocked`: cannot proceed until a listed business, legal, nutrition, or vendor decision is resolved.
