# Nourish local API service

This Node 24 service makes the client contract executable before infrastructure vendors are selected. Development defaults to memory persistence; setting `DATABASE_URL` selects PostgreSQL identity, profile, catalogue administration, entitlement, plan, feedback, weekly-operation, privacy, and job adapters.

It currently provides:

- one-time, expiring email magic links with per-email cooldown;
- opaque access and refresh tokens stored only as SHA-256 hashes;
- refresh-token rotation and access-token revocation;
- configuration-gated Sign in with Apple verification;
- authenticated profile reads and revision-safe updates;
- locally authenticated recipe draft, edit, submit, approve/publish, and reject boundaries;
- publication gates for ingredient verification, allergen derivation, nutrient review/effective dates, and production source licensing;
- reviewer-gated ingredient/conversion and immutable nutrient-source/record ingestion with audit evidence;
- separate author/reviewer identity and immutable published recipe versions with audit events;
- authenticated, idempotent weekly plan jobs that use the stored profile and only published catalogue snapshots;
- deterministic seven-day assembly, hard-exclusion diagnostics, explicit leftovers, plan reads, and adoption;
- account-owned locked regeneration with reasons, immutable plan history, and local-date scheduled next-week activation;
- authenticated meal ratings and weekly completion/change feedback with bounded controlled vocabularies;
- adopted active-plan reads, safe swap candidates, idempotent immutable-plan swap confirmation, normalized groceries, plan-derived prep, and revision-checked grocery/meal/prep mutations;
- server-owned entitlement snapshots, verified StoreKit transaction binding, App Store Server Notifications V2 ingress, and scheduled Apple subscription-status reconciliation that verify signed data, bind original transaction/account identity, allowlist subscription products, deduplicate events, and retain legitimate access during transient failures;
- operator-only aggregate KPI and cohort reads with documented formulas, freshness evidence, complete PRD filters, small-group suppression, and no identifiable rows;
- authenticated, idempotent app-version and bounded first-touch acquisition-dimension ingestion using server-derived account identity;
- operator-only exact-match user support lookup with reason capture, minimized read-only account state, and append-only found/not-found access audit;
- security-admin feature-flag configuration with deterministic percentage rollout, app-version targeting, bounded allowlists, emergency disable, optimistic versions, and append-only audit;
- operator aggregate CSV exports plus security-admin exact-match minimized account exports with idempotency, separate creation/delivery reasons, 24-hour expiry, private storage, and append-only audit;
- authenticated, idempotent account export and deletion receipts, with deletion disabling the account and revoking every active session;
- PostgreSQL authentication, profile compare-and-set updates, entitlement events, and atomic privacy request/job creation;
- leased background jobs with idempotent enqueueing, bounded retry, expired-lease recovery, and worker-type filtering;
- executable portable-export and account-erasure workers backed by a private object-store boundary;
- scheduled exact-object cleanup for expired customer and administrator exports with namespace validation and append-only retention evidence;
- durable plan requests that snapshot the request/profile revision, enqueue atomically, and materialize only complete safe weeks;
- transactional PostgreSQL recipe drafting, validation, independent review, publication, audit history, version succession, and reads for published immutable catalogue snapshots;
- PostgreSQL plan jobs/history/adoption, ratings/reviews, groceries, prep, and optimistic meal state;
- correlation IDs, no-store responses, bounded JSON bodies, and structured errors;
- readiness checks plus checksum-verified PostgreSQL migrations for account/profile, recipe catalogue, planning, weekly-loop, entitlement, privacy, and jobs.

Run `npm ci` once, then `npm test` with Node 24. The checked-in lockfile fixes the complete dependency graph. `npm start` listens on `127.0.0.1:8080`. In development only, the email delivery adapter prints the magic link to the terminal. Production suppresses this output, and no raw token is returned by the magic-link request endpoint.

For PostgreSQL mode, set `DATABASE_URL`; optionally set `DATABASE_REQUIRE_TLS=true`, `DATABASE_POOL_MAX`, and `DATABASE_AUTO_MIGRATE=true`. Migrations can also be run explicitly with `npm run db:migrate`. `GET /readyz` checks both the selected persistence dependency and the running release's checksum-verified migration manifest.

Production startup is fail closed: API and worker require PostgreSQL over TLS, authenticated application-level encryption over private S3-compatible export storage, planner locale/current-calculation allowlists, bounded numeric settings, no development admin key, and no automatic migration. A filesystem store requires an explicit staging-only production exception. Run `npm run config:check` with `NOURISH_PROCESS_TYPE=api` or `worker` to validate settings without printing secrets. `Dockerfile`, `.env.staging.example`, `../compose.staging.yml`, and `../docs/STAGING_DEPLOYMENT_METHOD.md` define the provider-neutral staging path; `../.do/app.staging.yaml` and `../docs/DIGITALOCEAN_STAGING_METHOD.md` specialize it for DigitalOcean without provisioning resources. `npm run staging:smoke` validates public liveness, durable readiness, no-store responses, and correlation headers after deployment.

Run the worker separately with the same `DATABASE_URL`, encryption key ring, and private-object namespace as the API, plus `npm run worker`. S3-compatible mode uses `NOURISH_PRIVATE_OBJECT_STORE=s3`, bucket, region, optional safe prefix/HTTPS endpoint, and the AWS SDK's workload-identity or standard secret-manager-injected credential chain. `NOURISH_PRIVATE_OBJECT_SSE` can be `AES256` or `aws:kms` for an additional AWS layer, or `none` for providers such as DigitalOcean Spaces; application-level AES-256-GCM encryption with object-key authentication remains mandatory in production in every case. Key rings support read-compatible rotation by retaining prior named 256-bit keys while a new key is active. The worker handles `plan.generate`, `account.export`, and `account.delete` and scans every minute for expired customer and administrator export objects. Cleanup accepts only exact expected object keys; account deletion paginates the complete safe account prefix; both clear database references only after physical deletion and append success/failure evidence. When `NOURISH_APP_STORE_RECONCILIATION_ENABLED=true`, the worker also scans due subscriptions and handles leased `entitlement.reconcile` jobs through Apple's official server library. Configure the issuer, key ID, private-key path, bundle ID, numeric Apple app ID, allowed subscription product IDs, and Apple root-certificate paths documented in `docs/ENTITLEMENT_RECONCILIATION_METHOD.md` before enabling it. Customer export files expire after seven days; signed download delivery and live bucket/replica retention validation remain deployment work.

Production planning also requires `NOURISH_PLANNER_ELIGIBLE_LOCALES` and `NOURISH_PLANNER_NUTRITION_CALCULATION_VERSIONS` as comma-separated allowlists on both the API and worker. Startup fails closed when either is missing in `NODE_ENV=production`. Only published reviewed snapshots matching both lists can enter generation or swap ranking. `wellness-score-v3` then applies the whole-week serving contract: ±5% daily calories where feasible, ±3% weekly calories, and configurable optional-protein tolerance, with explicit relaxation diagnostics when immutable reviewed serving bounds make a soft target impossible.

Production magic-link delivery uses the provider-neutral boundary. Initial staging selects `NOURISH_EMAIL_PROVIDER=brevo`, a verified `NOURISH_EMAIL_FROM`, and a secret-manager-injected `NOURISH_BREVO_API_KEY`; Postmark remains available through `NOURISH_POSTMARK_SERVER_TOKEN`. Both adapters send text and HTML, expose no provider error detail, use provider idempotency where available, and remove an undelivered token if the provider rejects the request. Brevo must have anonymous transactional tracking and a reviewed short log/content-retention period enabled before live sends; Postmark tracking is disabled in each request. `NOURISH_MAGIC_LINK_URL_PREFIX` defaults to the registered `nourish://` callback and may later move to an approved HTTPS universal-link origin. Development keeps the in-memory capture and terminal callback for local phone testing. See `../docs/EMAIL_DELIVERY_METHOD.md`.

For local development, catalogue administration is disabled unless `NOURISH_ADMIN_KEY` is supplied; that fallback additionally requires `x-nourish-admin-key` and `x-nourish-admin-id`. Reviewer-gated `POST /admin/v1/ingredients` and `POST /admin/v1/nutrient-records` populate verified content and provenance before recipes can be submitted. `GET /admin/v1/catalogue/content` restores verified ingredients, conversions, immutable nutrient values, and source provenance for the Control Room library. `GET /admin/v1/catalogue/queue` returns open work with validation and evidence, while `GET /admin/v1/catalogue/audit` returns combined ingestion and recipe decisions. In PostgreSQL mode these paths are durable. Set the exact dashboard origin with `NOURISH_ADMIN_ORIGIN` for narrowly scoped development CORS; the static key remains a development fallback and is not a substitute for configuring the workforce identity verifier and audit-retention operations.

The production-shaped alternative exchanges a configured workforce identity assertion at `POST /admin/v1/auth/session`, requires an `mfa` authentication method, and returns an eight-hour hash-only bearer session. `GET /admin/v1/auth/session` reads any active granted administrator identity and `POST /admin/v1/auth/revoke` ends the session. Every admin route enforces its persisted role and records granted or denied access with the correlation ID. Provision identities and reasoned grants using `npm run admin:provision`; the required environment values are documented in `docs/ADMIN_SECURITY_METHOD.md`. The external identity verifier and company sign-in UI remain deployment work, so the shared key must stay local-only.

Operator-gated `GET /admin/v1/plan-runs` supports state and run/user/correlation/error search, and `GET /admin/v1/plan-runs/{id}` returns the latest detail. The projection includes exact generator/scoring/rule versions, candidate and rejection counts, nutrition-tolerance pass/excess/relaxation evidence, typed failure, correlation, duration, immutable plan outcome, and background-job attempt/lease evidence. Stored profile snapshots and raw deterministic seeds are deliberately excluded; only the seed hash may be returned for reproducibility evidence.

Operator-gated `GET /admin/v1/subscriptions` supports reconciliation-status and user/product/environment/error search, while `GET /admin/v1/subscriptions/{userID}` combines the current server access decision with verified Apple events, notification ingress, reconciliation jobs, and append-only operator actions. Raw app-account tokens, complete transaction identifiers, signed payloads, and credentials are excluded; the projection returns hashes or bounded references. `POST /admin/v1/subscriptions/{userID}/actions/retry` accepts a reason only for delayed or mismatched cases, transactionally queues a fresh verified Apple check, and records the operator/correlation evidence without manually changing entitlement access.

Operator-gated `GET /admin/v1/kpis` and `GET /admin/v1/cohorts` accept local start/end dates, timezone, subscription state, app version, acquisition source, diet type, population cohort, and cohort-grouping filters. Every KPI and funnel step returns its formula and freshness time. Results are aggregate-only, contain no email or user ID, and suppress non-empty populations below five. PostgreSQL mode derives the metrics from account, profile, subscription, plan, adoption, review, and meal-state tables. Authenticated `POST /v1/analytics/dimensions` records first/latest app version and a bounded first-known acquisition source; it derives identity from the bearer session and accepts no client user ID. See `docs/ANALYTICS_DIMENSION_INGESTION.md`.

Authenticated `PATCH /v1/analytics/consent` controls optional first-party product measurement and defaults to disabled. Both `POST /v1/analytics/events` and server-observed events require enabled account consent. The exact 26-event PRD catalogue enforces schema version, strict per-event properties, client/server authority, server-derived identity, hashed idempotency, and explicit expiry, and all 26 product actions are connected. Plan outcomes and weekly mutations emit only after authoritative success. Purchase, trial, and subscription transitions derive from verified Apple transaction, notification, or reconciliation data. Accepted meal feedback and weekly reviews contain only bounded rating/reason or completion/change fields; optional feedback notes are never copied into analytics. PostgreSQL retention defaults to 90 days through `NOURISH_ANALYTICS_RETENTION_DAYS` (allowed range 1–400), and the worker deletes expired rows hourly. See `../docs/ANALYTICS_EVENT_METHOD.md`.

Operator-gated `POST /admin/v1/users/lookup` requires exactly one internal user ID or verified email plus a specific support reason. `GET /admin/v1/users/{id}` offers the direct-ID form and requires `x-support-access-reason`. Both return a minimized operational account summary and an access receipt; neither exposes profile answers, meal history, tokens, complete Apple identifiers, or impersonation. Found and not-found attempts are transactionally written to an append-only audit, with the normalized lookup value stored only as a SHA-256 hash. See `docs/USER_SUPPORT_METHOD.md`.

Security-admin `GET /admin/v1/flags` returns versioned configurations plus their latest reasoned audit receipts. `POST /admin/v1/flags` creates or updates a flag with optimistic `expectedVersion`, and atomically stores the new state and append-only audit. Authenticated consumer `GET /v1/feature-flags?appVersion=...` applies emergency disable, normal enabled state, semantic app-version bounds, exact internal-user allowlist, then deterministic SHA-256 percentage bucketing; disabled values are withheld. See `docs/FEATURE_FLAG_METHOD.md`.

Operator `GET /admin/v1/exports` lists authorized aggregate exports plus the caller's own requests; security administrators can see account-level requests. `POST /admin/v1/exports` requires an idempotency key and creates `kpis`, `cohorts`, or security-admin-only `support_account` CSV. Account creation requires exact identity and a reason, and `GET /admin/v1/exports/{id}/content` requires a separate `x-export-access-reason`. Files expire after 24 hours and are stored only through the configured private S3-compatible store in production PostgreSQL mode. See `docs/ADMIN_EXPORT_METHOD.md`.

`POST /v1/plans` requires an authenticated user, a stored profile, and an `idempotency-key` header. Memory mode completes deterministically inline; PostgreSQL mode returns `queued` and the worker advances it through `generating` to `succeeded` or a typed `rejected` state. The database starts with an empty catalogue, so the correct result is `CONTENT_INSUFFICIENT` until published reviewed versions are ingested. `GET /v1/plans/{id}` reads a job or plan, `GET /v1/plans/history` reads immutable lifecycle history, and `POST /v1/plans/{id}/adopt` requires a separate idempotency key. A first plan activates immediately; future renewal waits for its local start date.

The weekly loop adds `GET /v1/plans/active`, `GET /v1/plan-items/{id}/swaps`, idempotent `POST /v1/plan-items/{id}/swap`, `PATCH /v1/plan-items/{id}/status`, `GET/PATCH /v1/grocery-lists/{id}`, and `PATCH /v1/prep-tasks/{id}`. In PostgreSQL mode, active reads, safe candidates, immutable confirmed-swap succession/audit/adoption, grocery mutations, meal state and prep state are durable. Confirmation atomically recalculates groceries/prep and preserves only compatible operational state. `POST /v1/feedback` stores ownership-validated meal ratings and weekly reviews durably in PostgreSQL mode.

`GET /v1/entitlement` returns the last server-verified access decision and reconciliation status. Authenticated `POST /v1/entitlement/app-account-token` issues stable StoreKit account identity and `POST /v1/entitlement/transactions` verifies and binds a StoreKit transaction JWS. Configuration-gated `POST /v1/app-store/notifications/v2` is the unauthenticated Apple delivery endpoint; its signed payload is verified before any lookup or state change. `POST /v1/account/export` and `DELETE /v1/account` require idempotency keys and return queued receipts. Deletion additionally requires the exact `DELETE` acknowledgement, accepts an optional bounded reason, disables the user, and revokes all sessions before returning. App Store subscription cancellation remains a separate Apple-managed action.

Without `DATABASE_URL`, the running adapter is intentionally in-memory and restart clears all state. With `DATABASE_URL`, consumer/admin identity and session paths, profile/account/plan/feedback/weekly-state paths, catalogue content ingestion and author/review/publication, subscription/support/export operations, analytics dimensions, versioned feature flags, account-bound push registrations, access/change audit, shared privacy-safe authentication abuse counters, and background jobs are durable. The production database starts empty and requires licensed source selection plus qualified human review before content is loaded. The guarded local stack described in `../docs/LOCAL_END_TO_END_METHOD.md` instead loads visibly synthetic fixtures and verifies the release migrations plus authentication, profile persistence, queued worker generation, independent plan-ready notification handling, adoption, groceries, and prep against PostgreSQL 16. App Store notification/transaction ingress, scheduled reconciliation, APNs delivery, and transactional email delivery are implemented but configuration-gated. Managed-database TLS, backup/restore, failover, limiter-threshold validation, and live sender-domain deliverability still belong in staging. Workforce identity-provider configuration, approved production attribution, live Apple credentials/products/App Store Connect endpoint and sandbox fixtures, live bucket policy/workload identity/replica-retention validation, observability, backups, and recovery controls remain.
